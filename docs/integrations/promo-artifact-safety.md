## Intent and implemented contract

Reject credentialed, query-bearing, fragment-bearing, redactor-altered or malformed URLs and nonempty arbitrary details at the shared store boundary, with safe error messages. Bind later lifecycle records to account, kind, exact URL and any known object ID under the append lock. Reject any redaction that changes a bound identity. Omitted object IDs retain prior known identity. New pending cleanup requires a recorded private state, but direct deletion and legacy public pending → deletion retain the recorded visibility rather than inventing a private transition. A `cleanup_verified` event requires a prior `deleted` event and a literal true flag; a `deleted` event can itself carry literal true when the caller has verified deletion, while the default false is not verification. Explicit `recover_legacy_url` lets an operator attest a same-object safe canonical replacement for an unsafe historical URL, with locked exact-old-URL matching and no unsafe URL copied into the new row; it preserves state and never rewrites historical bytes. Preserve incomplete or corrupt history and reject further writes; an fsync failure leaves append outcome uncertain. Read views remain tolerant and are not integrity checks.

## Blockers, caveats and deferred work

- Semantic privacy cannot be proven from syntax: opaque secrets and sensitive share links in URL paths or short labels, or embedded query keys not recognized by the heuristic, can be indistinguishable from valid text. Credential-shaped descriptions can be rejected, and existing redactor heuristics may reject other text. Callers remain responsible for supplying non-secret inputs. Recovery requires caller verification of same-object identity, not just stripping a query. Conflicting old identities, unsafe old labels, or absence of a safe replacement require separate reconciliation; old bytes and discovery reads may still expose historical secrets and require separately authorized audit/remediation.
- Published BBH CLI `agents/public_artifacts.py` `_validate_cleanup_event` still requires `--visibility private`, and pending before deletion; it rejects direct public deletion and legacy public-pending recovery. Its `_validate_canonical_url` also rejects legacy query inputs and it exposes no recovery command. Coordinate a separately reviewed BBH follow-up to expose safe explicit recovery and support direct deletion/verification without falsely recording private visibility; align `skills/public-artifacts/SKILL.md` and its tests. No BBH repository was edited here.
- Discovery reads skip malformed lines; the write path rejects corrupt history. Advisory locks coordinate cooperating processes on one stable filesystem inode, not uncooperative writers or separate sync replicas.
- Existing beta consumers using nonempty `details`, mutable identity, new nonprivate pending events or query URLs now fail and require migration. The inspected BBH CLI passes empty `details`; its private → pending → deleted → verified workflow passed.
- Provider FID raw namespace collision is outside this task and `reports.py` was not modified.
- Independent review is required before beta integration/promotion. If it identifies compatibility or privacy gaps, add reproducing regressions and rerun the full Core and CLI suites above.
